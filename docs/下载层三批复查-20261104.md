# 下载层三批复查报告（2026-11-04）

针对你自行实现的三批下载层改动（多 CDN + md5 + 分片引擎 / queued 排队 + 全局槽位 / 暂停真续传），做了一轮代码审查 + 沙盒测试 + 冒烟测试。结论如下。

## 总评

三批实现方向正确，与设计分级一致。审查发现 **4 个实质问题**（其中 1 个是「暂停不生效」的语义缺口、1 个注释与实现不符的并发缺口），已全部修复。沙盒 676 条测试全绿，冒烟通过。真机测试脚本就绪但因执行环境故障未跑完。

---

## 第一批：多 CDN 候选 + md5 校验 + 分片引擎（纯增益，零语义变化）

| 改动 | 实质作用 |
|---|---|
| 多 CDN 候选选优 | N 网 API 本就返回多个服务器，旧代码 `foreach … return 第一个` 把其余全丢。现在全部保留、直连失败立刻换下一个。最坏情况等于今天 |
| md5 校验 | `files.json` 里有 md5 就校验、没有就跳过。只影响「下到脏包」这一种情况 |
| 分片引擎 | 默认关（开关 + 自动降级），不开就是原来的 `ResumableDownload` |

**带来什么**：下载更快更稳；状态机、任务语义、安装链路一概不动。失败路径只会更好。这批评级为「零风险」是成立的。

---

## 第二批：queued 排队 + 全局槽位（中风险，配套项都已跟上）

| 改动 | 实质作用 |
|---|---|
| `TaskItem.Queued` 标志 | 三处闸门（更新流水线下载段、Nexus 隐藏窗口、Steam 会话）排队时置位。任务行显示**「等待中」**，不再显示「运行中 · 0.00 M/s」这种骗人组合 |
| 口径分离 | `RunningCount`（真跑）/ `QueuedCount`（排队）/ `ActiveCount`（含排队）。总进度条不再被排队任务的残值百分比拖倒退；悬浮胶囊显示「2 个任务进行中 · 3 个排队中」 |
| 缓存前缀四通道互通 | `direct-/nxm-/dep-/mod-` 四种落盘名都认文件身份。**挖出一个真缺口**：更新流水线落盘的 `mod-{id}-{fid}.zip` 原先不在缓存复用范围内——更新重试永远找不到包、整包重下一遍。已补，且更新前先查缓存、命中直接装 |
| 拆 `SemaphoreSlim(3)` | 旧版把「检查+取链+下载+安装」捆在一个 3 名额闸里，而安装是全局串行——有人卡在安装队列就白占一个下载名额，这就是批量更新「看起来卡住」的根源。现在三层各管各的：检查段靠网络层硬顶、下载段限 3 路、安装段出门排队 |
| nxm 回流认领 | 排队期也往 Active 表占位，防止「一个 mod 两条任务」复发 |

**带来什么**：批量更新不再假卡住；重试秒进安装（用缓存包）而不是重新下载；排队状态真实可见、可解释。设计文档点名的两个回归点（「一个 mod 两条任务」「重试又重下一遍」）都有用例覆盖。

## 第三批：暂停真续传（高风险，含本次修复的核心缺口）

| 改动 | 实质作用 |
|---|---|
| `ResumableDownload` 字节偏移续传 | 断点续传是真的（偏移量记录 + 续写），不是从头重下 |
| 下载段/安装段分离 | 暂停只对下载段有效，进安装段后暂停按钮消失（解压/复制没法「停字节再续」）——这正是设计里说的「要先做分离重构」，第二批的闸门拆分就是它的前置 |
| `CanPause` 口径 | 安装段不显示暂停按钮，避免「暂停发生在安装段、点继续重装一遍」的尴尬态 |

**带来什么**：暂停终于真的停得下来，继续从断点走。但这批改动压在最常用的路径上（暂停/继续、重试、批量更新），风险确实最高。

---

## 审查发现并修复的 4 个问题

1. **暂停对更新任务完全无效**（最重要）：`UpdateOne` 的取链、下载、排队全传 `CancellationToken.None`——按了暂停照样下载，与第三批设计完全相悖。已全接 `task.Cts.Token`（排队等待、`ResolveDownloadUrlAsync`、`DownloadWithTask` N网/GitHub 两路）。
2. **`TaskItem.Queued` 会落盘**：没加 `[JsonIgnore]`，重启恢复后残留假排队标记。已补（与 `Installing` 口径一致）。
3. **queued 免疫看门狗靠调用点自律**：`IsZombie` 原先只扫 running，排队豁免依赖每个调用点记得 `BeginLongRunning`。现在硬排除 `Queued`，不靠自觉。
4. **安装段没进全局锁**：注释宣称「安装段全局串行（`_installGate`）」，但 N网/GitHub 两处安装段实际都没拿锁——批量更新时安装段会无限并发（同时解压多个包、同时写 Mods 目录）。正是设计里「要单独给安装留一个槽」那条。两处已补 `EnterInstallGateAsync`。
