# 自更新清单签名

> 一句话：**我们给"更新包是不是官方的"这件事找一个不依赖在线配额、也不依赖第三方镜像的答案。**
>
> 背景是审计第 10 条（"更新包拿不到官方 digest 时还校验吗 → 零校验直接执行"）。
> 完整背景见 `CHANGELOG.md` 与本文件末尾的"来龙去脉"。

---

## 一、要解决什么

自更新会下载一个 120MB 的 `setup.exe` 并**以你的权限执行它**。判断它是不是官方的，
只能靠校验值（sha256）。而校验值以前只有一个来源：

| 通道 | 什么时候走 | 能拿到 sha256 吗 |
|---|---|---|
| GitHub API | 正常情况 | **能**（release asset 上的 `digest`） |
| HTML 页面回落 | API 被限流（匿名配额 60 次/小时/IP）时才走 | **不能** —— 只能抠出下载链接 |

下载还要走 `ghfast.top` / `gh-proxy.com` / `ghproxy.net` 三个第三方镜像（直连 GitHub 在国内
经常超时），而 **HTTPS 只到镜像，不是端到端到 GitHub**。

于是出现这条路径：**API 限流 → HTML 回落 → 走镜像下一个包 → 零校验直接执行**。
这在国内是常态路径，不是边角情况。

现在加第三条通道：**签名清单**。

---

## 二、清单长什么样

两个文件，放在同一个目录下：

```
latest.json        纯数据（几百字节）
latest.json.sig    对 latest.json 原始字节的签名（base64 文本，88 字符 + 换行）
```

`latest.json`：

```json
{
  "schema": 1,
  "version": "1.3.0",
  "sha256": "bfc48b88b655d03dffcfc3f4d2a0894c12c331be8210bc85ec46f4091f587c2e",
  "size": 127531439,
  "url": "https://github.com/MLD-yu/JuniGrid/releases/download/v1.3.0/JuniGrid-cn-v1.3.0-setup.exe",
  "published_at": "2026-11-05T09:52:55Z",
  "key_id": "2026-01"
}
```

**签名的是原始字节，不是"重新序列化后的 JSON"** —— 后者会踩"键序/空白/换行算不算进签名"的坑。
两个文件分开就是为了不做规范化。

签名文件用 base64 文本而不是 64 字节二进制：文本在 GitHub Pages / raw / 镜像 / git push /
文本模式传输里都不会被改写（二进制遇到换行转换、编码猜测就废了）。

### 算法

ECDSA P-256 + SHA-256，签名是 IEEE P1363 定长 64 字节（r||s）。

- 选它是因为 **.NET 自带**（`System.Security.Cryptography`），不引 NuGet、不依赖外部工具；
- 换语言重实现时按 **P1363 r||s 定长** 对齐即可（DER 序列化的 ECDSA 签名不通用）。

## 三、私钥在哪、怎么保管

| | |
|---|---|
| 私钥 | `E:\junigrid\keys\junigrid-manifest-2026-01.pem`（**仓库外**） |
| 公钥 | `JuniGrid.Manifest/ManifestTrust.cs` 的 `PublicKeySpkiBase64`（进仓库） |

**纪律**（这几条比技术细节重要）：

1. 私钥绝不入库、绝不进 CI 日志、绝不贴在聊天里、绝不放会被同步的网盘。`.gitignore` 已加
   `*.pem` 兜底，但那是最后一道防线，不是第一道。
2. **离线备份两份**。私钥丢了 = 之后再也无法签新清单（老公钥还在，但发不了新版），不可逆。
3. 发版机上不要留长期在线的私钥副本：用完就收走。
4. 轮换：把新公钥追加进 `ManifestTrust.KnownKeys`，等上一版应用基本铺开后再停用旧的那把。
   （老版本应用不认新公钥，所以切换时机要等铺开。）

## 四、发版流程

**顺序很重要：先把安装包传到 GitHub Release，再生成清单。**
因为清单里的 sha256 必须和真正发出去的那份字节一致 —— CI 里另 build 一份再签，签的是另一个文件。

```powershell
# 1) 传安装包到 GitHub Release（v1.3.0 的 JuniGrid-cn-v1.3.0-setup.exe）

# 2) 生成 + 签名 + 自检
.\installer\publish-manifest.ps1

# 3) 推到托管点（GitHub Pages，需要 gh CLI 已登录）
.\installer\publish-manifest.ps1 -Publish
```

脚本做的事：找安装包 → 抠版本号 → 算 sha256/大小 → 写 `latest.json` → 签名写
`latest.json.sig` → **用内置公钥自检一遍**（不过就中止）→ 可选推到 `gh-pages` 分支。

手工做也行：

```powershell
dotnet run --project tools\JuniGrid.ManifestSigner -- make --exe <setup.exe> --version 1.3.0 --outdir dist-tmp --key E:\junigrid\keys\junigrid-manifest-2026-01.pem
dotnet run --project tools\JuniGrid.ManifestSigner -- verify --manifest dist-tmp\latest.json --sig dist-tmp\latest.json.sig
```

### 托管点放哪

清单只有几百字节，**流量约等于零** —— 安装包本体仍然走 GitHub + 镜像，不用搬。

| 方案 | 说明 |
|---|---|
| GitHub Pages（`gh-pages` 分支） | 零运维，脚本 `-Publish` 直接推。`*.github.io` 在国内经常连不上 → 当备用 |
| 腾讯 EdgeOne Pages | 免备案、有境内节点，推荐做主源 |
| 自己的域名 + 静态托管 | 想更自主就这个（要备案） |

应用端的托管点列表在 `JuniGrid/Services/SelfUpdateManifest.cs` 的 `BaseUrls`，
加一条就行 —— **清单是签名的，加多少个源都不降低可信度，只提高可用性**。

## 五、应用端怎么用

`SelfUpdateService.CheckAsync()` 的通道顺序变成：

```
① GitHub API          → 有官方 sha256
② 签名清单            → 我们自己签的 sha256（API 限流时的首选）
③ HTML 页面回落       → 没有 sha256，只能退到"要用户再点一次确认"
```

几条硬规矩：

- **验签失败只丢这个源，不算整轮更新失败。** 否则有人污染一个托管点就能让所有人更新不了（DoS）。
- **清单不合规一律拒绝**（schema 不认识 / sha 不是 64 位十六进制 / size ≤ 0 / url 不是 https
  / 版本号看不懂）—— 半截清单绝不能被拿去当凭据。
- 清单给的 sha256 写进 `.done` 之后，`SelfUpdateService.IsVerified()` 判"有凭据" ⇒
  **不再弹「未校验完整性，仍要安装」**。也就是审计第 10 条那道"知情同意"的临时门，
  在走清单这条路时是关着的。
- 清单里的 `version` 比本机旧 ⇒ 不算更新（防重放：有人拿旧的已签名清单骗老用户装旧版）。

**「再点一次确认」那道门为什么先不删**：它是最后一道兜底。清单挂了 + API 限流 + HTML 回落
可用时，仍然会出现"零凭据的包"，这时拦住是必要的。等 Authenticode 证书到位、
改成验签之后，才轮到把它拆掉。

## 六、故障排查

| 现象 | 多半是 |
|---|---|
| 日志「清单验签不过」 | 托管点上的 `latest.json` 和 `latest.json.sig` 不是一对；或清单被改过；或托管点返回了错误页（比如 404 的 HTML） |
| 日志「清单内容不合规」 | `latest.json` 格式不对（多半是上传时损坏了） |
| 日志「清单通道失败」 | 托管点连不上（DNS/超时）—— 不影响更新，只是退回 HTML 回落 |
| 更新按钮提示「未校验完整性」 | 走的是 HTML 回落（既没有 API 也没有清单）—— 检查清单是不是发布到托管点了 |

本地自检：

```powershell
dotnet run --project tools\JuniGrid.ManifestSigner -- verify --manifest <latest.json> --sig <latest.json.sig>
```

## 七、和 Authenticode（SignPath）的关系

两者不冲突，是叠加关系：

| | 清单签名 | Authenticode |
|---|---|---|
| 解决 | 「拿不到官方 sha256」（可用性） | 「这包是不是我们签发的」（信任） |
| 成本 | 0 元，自己签 | SignPath 的**免费开源计划**对 GPL 项目免费（申请材料已备好：`docs/signpath-申请材料.md`） |
| 用户能看到 | 什么都没有 | 右键属性里显示「发布者 JuniGrid」、SmartScreen 不再拦 |

理想的终局是**两者都要**：清单解决"国内也能拿到凭据"，Authenticode 解决"用户敢不敢点"。
拿到证书后，把验签换成 Authenticode，再把「再点一次确认」那道临时门拆掉。

## 八、来龙去脉

- 审计第 10 条：「更新包拿不到官方 digest 时还校验吗 → 零校验直接执行」。
- 当时的临时处置：没凭据就不自动弹向导，气泡显示「未校验完整性，仍要安装」，**要用户再点一次**
  （`SelfUpdateService.IsVerified` + `SelfUpdateButton.razor`）。判据落在 `.done` 里，
  关掉应用再回来也绕不过。
- 那道门是**知情同意**，不是**完整性验证** —— 字节本身仍然没被证明过。
- 本文件描述的清单签名补上的是后者：字节的可信度由我们自己签的清单担保。
