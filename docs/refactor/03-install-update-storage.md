## Risk notes

- `sealed` -> `sealed partial` is the only declaration change permitted. Any other edit during the split (reordering members, moving a field across a seam) silently changes static-initialisation order. `UpdateService.Http` (21) and `DownloadHttp` (887) are the two live hazards: if either field moves to a partial file whose initialiser runs later, the first `CheckSmapiAsync` call can observe `null`. Keep both fields in the keep-file.
- `private` members are visible across partial files, but `private static` FIELDS are not duplicated automatically. A copy-paste that lands `_installGate` (InstallService.cs:49) or `_gate` (StorageService.cs:40) in two files compiles cleanly and breaks mutual exclusion at runtime - no compiler error, no test failure until the concurrency test at WorkerCancellationAndOverlayTests.cs:43-73 runs. Diff for duplicated field names after the split.
- The StorageService 3-file split produces a 65-line file (`StorageService.CacheRoot.cs`), under the 300-700 target and against the "do NOT invent tiny files" rule. The 2-file alternative is: keep everything through line 586 in `StorageService.cs` and move only 588-837 (`MigrateCacheRootAsync` onward) to `StorageService.Migrate.cs` (~250 lines). Recommend the 2-file version unless `CacheRootRejection` is expected to grow.
- `InstallService.DependencyRanking.cs` is the only partial file with a clean exit criterion: it has zero outgoing calls to the other two halves. If a later change makes `RankByAuthor` call `ResolveDependencyDisplayAsync`, the split becomes a cycle and the seam should be revisited.
- `UpdateService.SmapiInstall.cs` and `UpdateService.Files.cs` are entangled one-way (installer -> files): `RunSmapiInstallerAsync` calls `DownloadToFileAsync` (944) and `ExtractWithRetryAsync` (901); `InstallSmapiZipAsync` calls `BackupMods`/`RestoreMods`/`TryDeleteBackup`. That is safe, but do NOT move `BackupMods` into the installer file "because the installer uses it" - StorageService.GetCategories reasons about the same `Mods-*` layout that `BackupMods` writes [JuniGrid/Services/StorageService.cs:107-132].
- The 475 tests must keep passing without edits. Every `internal static` member the fixtures call (`MayDiscardHalfPack`, `IsStaleRun`, `PremiumNeedsWebFallback`, `AuthorAffinity`, `NameMatchScore`, `PickDescriptionLink`, `RankByAuthor`, `SearchHitIdentifies`, `SavedDisplayStillTrustworthy`, `PageProvidesVersion`, `PageProvidesAnyVersion`, `UidSearchTerms`, `EnterInstallGateAsync`, `ExitInstallGate`) stays on the same type name `InstallService`, so no test change is needed. If any of them changes accessibility during the split, that is a defect.
- `StorageService.DirSize` must remain `internal`, not `private` - DepotDownloaderService.Apply.cs:319 calls `StorageService.DirSize`. If it moves to a partial and someone narrows it, the main app stops compiling.
- `ConfigService` static-adjacent hazard: `AtomicFile.WriteAllText` is called from a `ConfigService` static context at ConfigService.cs:75 and from the instance paths at 299/337. If Cluster A is consolidated, verify the ConfigService debounce loop (218-253) still owns its own dirty-version bookkeeping - `AtomicFile` does not touch `_savedVersion`.
- REAL regression risk if Cluster A / `ModService.WriteManifestAtomic` is consolidated: the retry cadence changes from 4 attempts at 50/100/150 ms (~300 ms total) to 5 attempts at 10/20/30/40 ms (~100 ms total). Under a Defender lock - exactly the case the comment at ModService.cs:741-743 describes - the new cadence gives up 3x sooner. Either keep `WriteManifestAtomic` as-is, or add a `retryDelayMs` parameter to `AtomicFile.WriteAllText` before consolidating.
- `TotalPlayMinutes` (ConfigService.cs:520) and the five `Portrait*` properties (ConfigService.cs:559-563) are load-bearing for a DIFFERENT app sharing `%APPDATA%\JuniGrid\junigrid.config.json` (documented at ConfigService.cs:551-558). Any cleanup that removes config properties breaks the older junigrid-blazor build. This is the single biggest trap in this area.
- `smapi-bridge` cannot be split or modernised without first proving the net6.0 reference set (game-bundled DLLs, `DisableImplicitFrameworkReferences=true`) resolves any new API. Treat it as frozen.
- If the `installer/JuniGridInstaller` files are touched at all, remember `InstallerWindow.xaml.cs` is one half of a generated `partial class`; adding a second hand-written partial is legal but pointless, and any member rename breaks the XAML-generated half at compile time.
