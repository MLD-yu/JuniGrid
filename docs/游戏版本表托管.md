# 游戏版本表托管

> 一句话：**把「星露谷版本号 ↔ Steam manifest」这张对照表搬到网上并签名，这样加一个游戏版本不用重新发版。**
>
> 只搬表，**不搬游戏**。游戏本体仍然由用户用自己的 Steam 账号从 Steam CDN 拉。

---

## 一、先划清边界：什么能放、什么不能放

| | |
|---|---|
| 版本号、Steam manifest GID、发布日期、兼容性备注 | **可以公开托管。** 公开元数据，SteamDB 上人人可查 |
| `Game1.exe`、`Content/`、任何重新打包的游戏本体 | **绝对不能。** 星露谷本体版权属 ConcernedApe；放到 GitHub / Gitee 就是盗版分发源，DMCA/投诉直接删库封号 |

另外两个现实原因也指向同一个结论：

- **体积**：51 个版本 × 每个几百 MB = 十几 GB 起。GitHub 单文件 2GB、仓库建议 5GB；Gitee 单附件 100MB、总 1GB。放不下。
- **速度**：国内下 GitHub 1GB 文件比 Steam CDN 慢得多。托管游戏本体连"更方便"这个初衷都达不到。

所以链路只有一条：**元数据你来发，游戏文件 Steam 来发。**

## 二、表长什么样、放在哪

```
JuniGrid/Assets/game-versions.json        仓库里的源文件（52 条，从新到旧）
JuniGrid/Assets/game-versions.json.sig    签名（本地生成，gitignore，不进库）
```

文件结构：

```json
{
  "schema": 1,
  "app_id": "413150",
  "depot_id": "413151",
  "updated_at": "2026-11-13T00:00:00Z",
  "notes": ["收录口径……"],
  "versions": [
    { "version": "1.6.15", "manifest": "4278718763097142923", "label": "正式版" },
    { "version": "1.6.14", "manifest": "1364246008775303529", "label": "上一正式版" }
  ]
}
```

**`versions` 的顺序就是语义**：从新到旧，下标即版本序号（0 = 最新）。
`TryGetVersionRank` 直接拿下标当序，版本比较、存档兼容判断、「当前是不是官方最新版」全依赖它。

> 顺序写错不会报错，只会**静默错**：1.6.10 被排到 1.5.6 后面 → 玩家从 1.6.10 的存档切到 1.5.6
> 时被判成"读得了"，一进档就闪退；反过来还会把真·最新版判成历史版，去锁 Steam 的 appmanifest，
> Steam 更新被卡成「磁盘写入错误」。所以改完**必须**跑一遍 `publish-catalog.ps1` 的校验。

单条字段：`version`（必填）、`manifest`（必填，纯十进制 uint64）、`label`（显示标签）、`note`（备注，程序不读）。

## 三、客户端怎么用：三层，优先级从低到高

| 层 | 位置 | 什么时候生效 | 谁能改 |
|---|---|---|---|
| ① 内嵌 | 编进 `JuniGrid.dll` 的程序集资源 | 首次启动、断网、所有托管点都挂 | 跟版本走 |
| ② 本机缓存 | `<缓存目录>\meta\game-versions.json(.sig)` | ①之上、联网前 —— 让"上次看到的新版本"断网时也还在 | 上次验签通过的在线副本 |
| ③ 在线 | GitHub Pages（和更新清单同一个目录） | 后台拉取成功且验签通过时覆盖①② | 你的签名 |

代码入口：`Services/GameVersionCatalog.cs`

- 启动时 `LoadDiskCache()` **同步**读缓存（5KB，可忽略），然后 `RefreshInBackground()` 后台拉在线副本。
- 在线那份和自更新清单用**同一个公钥**（`ManifestTrust.PublicKeySpkiBase64`）、同一个签名算法（ECDSA P-256 + SHA-256）。
- 托管点列表复用 `SelfUpdateManifest.BaseUrls` —— 加一个源只提高可用性，不降低可信度。

## 四、加一个游戏版本（日常流程）

星露谷发布了 1.6.16：

```powershell
# 1) 在 JuniGrid\Assets\game-versions.json 的 versions 数组**最前面**插一行
#    { "version": "1.6.16", "manifest": "<新 GID>", "label": "正式版" },
#    顺便把原来的 "正式版" 改成 "上一正式版"

# 2) 校验 + 签名 + 推送到 GitHub Pages（updated_at 会自动改成当前时间）
.\installer\publish-catalog.ps1 -Publish
```

就这两步。**不用改代码、不用重编译、不用发安装包**，所有老客户端下次启动就能在下拉框里看到 1.6.16。

manifest GID 从哪来：SteamDB 该 depot 的 `Manifests` 历史，或 `DepotDownloader` 的 `-manifest` 列表。

只想校验、不想发布：

```powershell
dotnet run --project tools\JuniGrid.ManifestSigner -- catalog --file JuniGrid\Assets\game-versions.json
```

### 什么时候需要动内嵌副本

内嵌的那份（①）只在**发新版应用**时才更新。没发版时老客户端里的①是旧的 —— 但③优先，
所以不影响"加新版本"。维护习惯建议：**发版前顺手把 1) 的内容同步进仓库**，这样新装用户首次启动
（还没联网）就能看到最新版本，而不是先看到一堆旧版本再刷新一次。

## 五、安全模型（几条硬规矩）

1. **验签不过只丢这一个源，不改任何东西。** 否则有人污染一个托管点就能让所有人看不到新版本（DoS）。
2. **不合规一律拒绝**（fail closed）：`schema` 不认识 / `app_id` 不是 413150 / `manifest` 不是纯数字 /
   版本号含空格或斜杠 / 同名版本重复 / 同一 GID 重复。半截的表绝不能被拿去当凭据。
3. **版本号只允许字母数字和 `. - _`。** 这个值会直接进缓存目录名（`StagingDirFor` 用它拼 staging 路径），
   而表的内容是远端可替换的 —— 路径拼接口子必须在解析层就关上，不能指望后面每个调用点自己 sanitize。
4. **防重放：驳回比本机更旧的表。** 签名只证明"这份表是作者签的"，不证明"它是最新的"。
   一份旧的已签名表被重放（CDN 缓存、中间人、滞后镜像）时，`IsLatestOfficialManifest` 会拿错的最新型号，
   把用户的真·最新版判成历史版 → 去锁 appmanifest → Steam 更新卡成「磁盘写入错误」。
   判据：本机最新版本在新表里排到第 2 位之后就算"更旧"，驳回并记日志。
   （新表里新增、删除、改名都不受影响 —— 那是作者的正常操作。）
5. **本机缓存也要验签。** 磁盘上的文件别的进程能改，读回来照样过一遍签名。
6. **原子替换。** 快照整体 `Interlocked.Exchange`，读者要么看到旧表要么看到新表，
   不会读到"一半是 1.6.16 表、一半是 1.6.15 表"的下标。

## 六、排错

| 现象 | 多半是 |
|---|---|
| 日志 `版本表验签不过（<url>）` | 托管点上的 json 和 .sig 不是一对；或 json 被改过；或返回了 404 的 HTML |
| 日志 `版本表内容不合规` | json 字段写错（manifest 带了非数字、版本号重复、schema 不对） |
| 日志 `驳回更旧的版本表` | 托管点上是旧文件（Pages 没构建完 / CDN 缓存），或本地缓存比线上新（正常，忽略） |
| 日志 `版本表通道失败` | 托管点连不上（国内连 github.io 是常态）—— 不影响使用，退回缓存/内嵌 |
| 版本下拉里没有最新版本 | 先看日志有没有"版本表就绪（… 最新 X）"；再确认 `publish-catalog.ps1 -Publish` 是否真的生效 |
| 发版后新装用户看到旧列表 | 内嵌那份没跟着更新 —— 见上面「什么时候需要动内嵌副本」 |

日志标签统一是 `VersionCatalog`。

## 七、和自更新清单的关系

两者共用签名机制，但是**两个独立文件**，各发布各的：

| | `latest.json` | `game-versions.json` |
|---|---|---|
| 描述什么 | 安装包在哪、sha256 是多少 | 哪个游戏版本对应哪个 manifest |
| 谁需要它 | 自更新流程（下载并执行安装包） | 版本管理弹窗、下载历史版本 |
| 更新频率 | 每次发版 | 星露谷每次更新（**不需要发版**） |

分开的好处：改游戏版本表不会牵动自更新的凭据，反之亦然。签名私钥、公钥、托管点、验签实现全都是同一套，
所以 `docs/自更新清单签名.md` 里关于密钥保管、轮换、base64 签名文件的说明同样适用于本文件。
